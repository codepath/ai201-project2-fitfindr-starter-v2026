# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:**
The search uses keyword matching, so some reasonable phrasings may not match the
listing data. Once a listing is found, the remaining tool calls should normally
complete successfully.

---

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:**
The empty-search branch is deterministic and does not depend on model-generated
text. Every empty result should therefore stop the loop reliably.

---

## 3. Something about state

In 5 of 5 successful runs, `session["selected_item"]` is the same listing
dictionary that was passed as `new_item` to `suggest_outfit`.

**Why this target:**
The selected listing is the main state passed between tools. A 5 of 5 target is
reasonable because the agent should always pass the item stored in the session,
not a newly recreated or different item.

---

## 4. Something about the fit card

In at least 4 of 5 successful runs, the fit card is a non-empty string that
mentions the selected item's title and price.

**Why this target:**
The model may phrase the card differently each time, but it should still include
the two concrete facts needed to identify and describe the item. Four of five
allows for occasional model variation while requiring consistent useful output.

---

## 5. Your choice

For 5 of 5 searches with a `max_price` value, every returned listing has a
price less than or equal to that maximum price.

**Why this target:**
The maximum-price filter is implemented locally and should be deterministic.
Unlike model-generated outfit text, it should never vary between runs.

---


## Capstone criteria

Written before any capstone results existed. Each is checked in 3 separate
trials of `python capstone_eval.py`; a criterion is MET only if the target
holds in all 3 trials. Criteria 1–3 are about the extension (numeric sizes).

### 1. Numeric sizes are parsed to the right value

For the five numeric-size queries (S1–S5), the parsed size equals the expected
value (e.g. "size 8" → `US 8`, "waist 28" → `W28`) — 5 of 5, in every trial.

**Why this target:** The size is stated explicitly in the query, so parsing
involves no guessing. It is a fixed rule that should give the same answer
every time, and every later step (the search filter, which listing is chosen,
the fit card) depends on it. One wrong parse breaks the whole run.

### 2. Every returned listing matches the requested numeric size

For the four in-stock numeric-size queries (S1–S4), the search returns at
least one listing and every returned listing's size matches the requested
size (a `US 8` request never returns `US 8.5`) — 4 of 4, in every trial.

**Why this target:** The search filters on the parsed size against the
listings data, so each query has one clear correct answer and no model is
involved. A single wrong-size listing means the user is shown shoes or jeans
they can't wear.

### 3. A numeric size nobody stocks stops early and says so

For a numeric-size query no listing matches (S5, "canvas sneakers size 12"),
the search returns 0 listings, the agent stops before `suggest_outfit` (no fit
card), and the message shown to the user names the size (`US 12`) — 1 of 1,
in every trial.

**Why this target:** An out-of-stock size is a normal case, not a rare one,
so it has to be handled every time. It is the same filter as criterion 2: if
this ever let another size through, criterion 2's filter would be wrong too.
When nothing is found the agent must say clearly that the size isn't
available, not invent an outfit for an item that doesn't exist.

### 4. The original queries still work

The two original queries (R1 "vintage graphic tee under $30, size M", R2
"vintage jacket under $25") are parsed correctly and end in a fit card — at
least 1 of 2, in every trial.

**Why this target:** The fit card is generated by the model, which is not
deterministic, so an occasional failure is allowed. But the change must not
break the original system: at least half must succeed in every trial, and
0 of 2 in any trial counts as a regression.

### 5. Malformed requests get a 400, not a 500

An empty query (F1) and a request body that isn't JSON (F2) both get HTTP 400
with a message saying what to send, never a 500 — 2 of 2, in every trial.

**Why this target:** A bad request is a problem with the input, not with the
system, so `serve.py` should reject it immediately with a clear error. This is
plain code with no model involved, so there is no reason for it to fail even
once.
